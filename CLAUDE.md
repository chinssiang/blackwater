# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Design Context

Design work is grounded in two root files, read by agents before any UI work:

- **PRODUCT.md** — strategy: register (`brand`), users, purpose, brand personality, anti-references, design principles, accessibility.
- **DESIGN.md** — the **canonical** visual system: theme and surfaces, colour tokens, the type ladder, spacing and the z-index ladder, components, interaction states, motion, named anti-patterns, and the list of tokens that are dead or broken.

Consult both before UI work so changes stay on-brand. `DESIGN.md` is hand-maintained and guarded by `src/lib/design-doc.test.ts`; do not regenerate it from the codebase.

## Commands

See `package.json` scripts. Two things they don't tell you:

- Sanity Studio is embedded at `/sanity` and runs alongside the Next.js app on the same port.
- `npm run typegen` must be re-run after **any** Sanity schema change (`predev` does it automatically); it runs `generate:groq` and then regenerates `schema.json` and `sanity.types.ts`. All three are committed, and CI fails on a stale one.

## Architecture

This is a **Next.js 16 (App Router) + Sanity v5** project. Content is managed in Sanity and rendered via Next.js. The stack uses React 19, Tailwind CSS v4, Base UI (`@base-ui/react`, the shadcn default since July 2026 — see the note under Key Shared Components), and Motion (Framer Motion successor).

`scripts/` holds Node tooling run outside the app — `generate-groq-constants.mjs` (see Routing) and `audit-image-resolution.mjs`. One-shot data scripts, for work `defineMigration`'s per-document callback can't do, also go there and are deleted once every dataset has run them. Reusable migrations live in `src/sanity/migrations/` and run via the Sanity CLI.

### Sanity Integration

**Schema naming conventions:**

- `g-*` = global singletons (header, footer, announcement, author, team-member)
- `p-*` = page singletons or document types
- `settings-*` = settings singletons (general, color, menus, integrations, redirect)

**Singleton documents** (non-duplicatable, single-instance): the `singletonDocuments` array in `sanity.config.ts` is the authoritative list — `gHeader`, `gFooter`, `gMobileMenu`, `gToolbar`, `gAnnouncement`, `gNewsletter`, `pHome`, `pContact`, `pFaq`, `pSizeGuide`, `pNewsletter`, `p404`, `pProductIndex`, `settingsGeneral`, `settingsIntegration`, `settingsConsent`, `settingsCart` (document-localized; lives under Products in the Studio). Being in it removes the "duplicate" and new-document actions. Note that `gAuthor`, `settingsBrandColors`, `settingsMenu` and `settingsRedirect` are single-instance in practice but are **not** in that array, so the Studio still offers to duplicate them. Type names don't all follow their filenames — `settings-integrations.ts` defines `settingsIntegration` (singular) and `settings-color.ts` defines `settingsBrandColors`.

**Document types** (multi-instance, slug-based):

- `pGeneral` — Generic pages at `/<slug>`
- `pBlog` / `pBlogIndex` / `pBlogCategory` — Blog system (routes currently disabled)
- `pProduct` / `pProductCategory` / `pProductCollection` — Product system (field-level i18n — see Localization below)
- `pEvent` / `pEvents` / `pEventCategory` / `pEventRole` / `pEventStatus` — Event system
- `pBrand` — Brand entries
- `gTag` — Tags referenced from product metadata lists
- `gTeamMember` — Team member profiles
- `gLocation` — Event venues (referenced by `pEvent`; carries `address` + `geo` for structured data)
- `gFaq` — Global FAQ entries (deliberately **not** document-localized: a question's identity and its place in the list are locale-invariant, so one document carries every language in inline internationalized arrays — the `question` and the `answer` — exactly like `gSizeChart`'s measurements. It carries **no `order` field**: order is a property of the _set_, not the entry — see `gFaqList` below. Referenced from `gFaqList` sets, never directly by a page.)
- `gFaqList` — A named, ordered **FAQ set**: the list of `gFaq` references itself, as a document. Deliberately **not** localized, for the same reason `gFaq` is not — which questions belong together, and in what order, is one fact in every language. Referenced by `pFaq.faqSet` (the `/faq` page) and by a `faqBlock` page module's `faqSet`, so one set can appear in several places and a page needing a different selection points at a different set. This exists because holding the list inline meant one copy per page **per locale**: the two prod FAQ pages had drifted to the same fifteen questions in different orders. The set's `title` is a plain string — an editor-facing label for the picker, never rendered; the rendered section heading stays per-page on the `faqBlock` module.
- `gSizeChart` — Global garment size charts (deliberately **not** document-localized: measurements are locale-invariant, so numbers are stored once and only the text is translated via inline internationalized arrays — the fit `note` and each measurement's `label`). Referenced by `pProduct.sizeChart` (which opens the chart in a dialog on the product page, falling back to a `/size-guide` link when the chart has no table to show) and listed on `/size-guide`. Authoring mirrors the rendered table: `sizes[]` are the columns (free text, e.g. `XS…2XL`, or a single `One Size`) and each `rows[]` entry is **one measurement**, holding a `label` plus one `values[]` cell per size. A cell is `{ size, min, max? }`, so a chart mixes fit ranges (`34–36`) with single measurements (`32`) and both ends stay numeric for the cm/in toggle. **Cells are matched to columns by `size`, never by array position** — reordering or inserting a size can't shift a row's numbers under the wrong heading, and `values[]` order is irrelevant. A `Rule.custom` on `rows` blocks publishing unless every measurement covers exactly the chart's `sizes` (no gaps, strays, or repeats), so a typo'd size is a loud error rather than a phantom column. There is no preset measurement vocabulary — adding a measurement is content work, not a code change.

**Localization:** Two locales (`en`, `zh_tw`) defined in `src/lib/i18n.ts`. Page/global docs are localized at the **document level** via the `documentInternationalization` plugin (`src/sanity/i18n-types.ts` lists translatable types; fetched per-locale via the `byLocale()` GROQ helper). Short, referenced strings (e.g. `gLocation.name`, `pEventStatus.title`, `settingsGeneral.alternateName`) use **inline `internationalizedArray`** instead, resolved with `coalesce(field[language == $locale][0].value, field[language == "en"][0].value)` — in `queries.ts` that coalesce is the `locString()` / `locPT()` helper, not hand-written. Length is not the test, though: `gFaq.answer` is inline `internationalizedArrayPortableTextSimple`, because what decides this is whether the _document_ has a locale. A page does; a referenced entry whose identity is the same in every language does not.

**The event family (`pEvent`, `pEvents`, `pEventCategory`) is FIELD-level localized too**, on the same machinery as the product family below — one document per event carries every language. The reason is different, though: an event is a single _occurrence_, so its start time, venue, crew roster and status can only have one value, and two documents per event meant two copies of facts that drifted (two events ended up with different start times per language). Prose lives in `internationalizedArray`s, including `internationalizedArrayPortableText` — `pEvent.content` is the FULL `portableText` type, so `'portableText'` is registered in `fieldTypes` alongside `'portableTextSimple'` in `sanity.config.ts`. Everything locale-invariant (dates, `locationRef`, categories, `statusList`, team assignments, images) exists once. Notes specific to events:

- **Both event sitemap entries need `locales`, not `language`** — `pEvent` derives it from `title[].language`, while `pEvents` (the index) advertises every locale because it renders an English fallback anywhere, the same treatment `pProductCategory` gets.
- **`/events-crew` sits outside the `[locale]` segment**, so it has no `$locale` to resolve against. Its queries use the `crewString()` helper in `queries.ts`, which coalesces **zh_tw first, then en** — the crew is Taiwan-based and the roster is written in Chinese. `locationRef.name` already worked this way; `title`, `subtitle`, `location`, `teamNotes` and `teamAssignments[].note` joined it. The crew view also used to count every translated event twice; one document per event fixed that.
- **`/events` renders one dataset two ways** — a list and a month calendar, behind a **single toggle button** in the sticky header. The button names the view you GET, not the one you are in: it reads CALENDAR while the list is showing. A lone control labelled with its own state cannot say which way it switches, which is the whole reason for that choice. ONE control, not a pair, because the 375px line already carries the month name and both month arrows: measured against the compiled CSS it leaves 67px spare, and that is also why the arrows keep `max-sm:hidden` on their labels — showing them needs 405px of a 343px line. The trade, taken deliberately: a button is not a tab set, so screen readers do not announce "tab 1 of 2". The button carries an `aria-label` naming the action instead (the visible word is contained in it, per WCAG 2.5.3), and deliberately **no `aria-pressed`** — it is an action, not a state. `PageEvents` owns the state both read: one `currentDate` clock, and one **month index** (`toMonthIndex`, an integer, not a `{year, month}` pair), so switching view keeps your place. **The switch itself cross-fades, through an `AnimatePresence mode="popLayout"`** — the only `mode` in the repo, and the reason is the height gap: at 375px the list is ~2350px and the calendar ~425px, so `popLayout` pins the leaving view `position: absolute` at the box it held and the arriving view takes its place in flow on the first frame, leaving nothing below to move. The default `sync` would sit the arriving view ~700px down the page until the fade ended; `wait` would collapse the container to nothing between the two. Four things this rests on. Both wrappers animate **exit only** and carry `initial={false}` — each view already owns its entrance, a wrapper fade-in would multiply two opacity curves, and a wrapper that starts hidden would put `opacity: 0` in the prerendered HTML and strand the whole view if hydration never ran. The wrapper around them is `relative`, because Motion positions the pinned element against its `offsetParent` and with no positioned ancestor that is the body. The list's own entrance delay is `CONTENT_ENTER_DELAY`, deliberately **shorter** than `VIEW_SWAP_DURATION`, so the rows are already climbing while the outgoing view is still visible — at the old 0.3s against a 0.2s fade there was ~100ms of blank page in between, which was the whole reason the switch still read as a cut. And `popLayout` works by injecting a `<style>` into `document.head`, which today's `style-src 'self' 'unsafe-inline'` allows; hardening the CSP to nonce-based (the TODO at the top of `next.config.mjs`) blocks that rule silently and the layout push comes back, fixable only by passing the nonce through `<MotionConfig>`. The cost accepted: when the arriving view is the shorter one the pinned view overhangs the container and paints over what follows for those 0.2s, so the toggle also resets scroll to the top the way the month arrows do. Do **not** reach for the View Transitions API here — `viewTransition` was removed from `next.config.mjs` deliberately, over a ~12.5s LCP render-delay on `/products`. The prev/next buttons deliberately mean different things per view: the list has no way to render a month with no rows, so it jumps to the next month that HAS events, while the calendar steps one month at a time (`stepMonth` in `PageEvents`, bounded by the `monthRange` beside it) because an empty grid says something real. Those bounds are the DATA's, not the events': backwards they stop at the query's own 12-month cutoff, since an empty grid past it would claim there were no events when we simply never asked; forwards the query holds everything, so paging on is honest. Clamping them to the event span instead is what made both arrows dead whenever every event sat in the current month. **The clock both views read wakes on transitions, not on an interval**: `PageEvents` schedules one `setTimeout` from `getNextEventClockTransition()` and re-arms on each wake-up, replacing a blind 60-second `setInterval` that re-rendered the whole grid and every list row once a minute for a byte-identical result. That function lives in `event-date.ts` beside the three readers whose answers flip at those instants — `isEventEnded`, `getDaysUntilEvent`, `getTodayKey` — because knowing WHICH instants they are means knowing which zone each counts in: days-until counts in the event's own zone while `getTodayKey` reads in the club's, so the rollover (`getNextDayStartInstant`) is asked once per timezone in play. **It answers with the first instant the answer DIFFERS, not the boundary** — `end + 1` for an event, since `isEventEnded` compares `end < now`, and midnight as-is for a rollover — which is what makes the result strictly greater than `now` by construction and lets the caller re-arm with no settling pad. Reporting the boundary instead needed one: a wake-up landing exactly ON an end rendered it as not yet ended and then, because the next scan wants an instant strictly after `now`, dropped that transition and left the row stale until the following day. Resolving every event's end up front to find the earliest costs 0.76ms for 89 events (measured — `date-fns-tz` caches its `Intl.DateTimeFormat` per zone, so the end-of-day fallback is ~6.4µs, not the ~65µs of an uncached construction), so there is deliberately no pre-filter. `/events-crew` still uses the blind interval; extracting a shared hook was judged not worth it for two call sites. **`<EventsCalendar>` is NOT code-split, and that call is now a much closer one than it was.** Most of what the calendar needs is already in `PageEvents`' own graph (`lib/calendar`, `date-fns-tz` via `event-date`, `EventStatusPill`, `CustomLink`, `event-location`, `event-status`, `routes`, `dateFnsLocale`, `lib/animate`), which is what once left ~1KB gzip of unique component to weigh against a loading boundary and a fetch on the first toggle. **The desktop day popover broke that.** `@base-ui/react/popover` is imported nowhere else on the route, so the static import in `EventsCalendar` adds a measured **~58KB raw / ~20KB gzip** on top of the `@base-ui/react/dialog` the header chrome already pays for — roughly three times what the commit before this branch removed from the same route by making `tabsTriggerVariants` a leaf module. Three things make it avoidable rather than inherent: `view` defaults to `'list'`, so the calendar renders only after a toggle; the popover branch is reached only when `isDesktop`, so every phone visitor downloads all of it and can never open one; and `PageEvents` is already `'use client'`, so a `next/dynamic` boundary there is a real `import()` (unlike the Server-Component case `HeroWaveLazy` exists for). If you split it, split `<EventsCalendar>` itself on the `LocationCurrentTimeLazy` pattern and the popover goes with it. `page.tsx` passes the query result through `omitPageMetadata` and the grouping happens client-side — it used to send a second pre-grouped copy of every event in the same payload. **`<EventsCalendar>` splits its interaction model at `lg`**: above it a day cell is a **popover trigger** and its events open anchored to the cell; below it the cell stays a button that fills the panel beneath the grid. That reverses what this bullet used to say, and geometry forced it — six rows of `min-h-28` put the panel up to ~700px below the cell that was clicked, so on desktop the click appeared to do nothing. It is **not** the alternative that was rejected (chips-as-links on desktop plus a select-button on mobile): the chips are still labels inside the control, each day is still exactly **one** control at every width, and `DayEventRow` is still the only place the view opens an event from — both branches render it, through the shared `DayDetail`. Five consequences. The branch is chosen in **JS** (`useMediaQuery`, `(min-width: 64rem)` in **rem** so it agrees with `lg:`), because a portalled popup cannot be CSS-hidden without leaving a trigger that opens an invisible dialog and moves focus into it. The prerender therefore always bakes the **mobile** branch and a desktop client swaps the cells after hydration — invisible **only because** the view now lands with nothing selected and nothing open, which is why `DayCell` builds one `cellClass`/`cellContent` for both controls, and why the old "next upcoming day, else the last day with events" default is **gone**; its two null states are now different strings (`calendar.selectDayPrompt` when a month has events and none is picked, `emptyMonth` when it has none — the latter deliberately rendered _outside_ the `lg:hidden` wrapper so desktop still says it). The panel stays in the DOM at every width behind `lg:hidden`, since JS-gating it would flash the prompt on a desktop first paint (and `display: none` takes it out of the a11y tree, so the hidden panel is neither focusable nor announced). The desktop branch never calls `selectDay`, because moving the calendar to a padding day's own month would move or destroy the popup's anchor — so a desktop click writes no `selectedDay`, and a phone selection carried past `lg` by a resize is simply lost; that is also why the panel's fill is `max-lg:`-scoped while the popover's is read off Base UI's own `data-popup-open`. Two structural details inside the popup, both of which look like tidy-ups: the scroll lives on `DayDetail`'s `<ul>` (`min-h-0 overflow-y-auto`) and the popup itself is `overflow-hidden`, so the day heading and the close button stay put while the events move under them — putting the scroll back on the popup scrolls both away, and the `<ul>`'s two classes are inert in the panel, where a block parent with no height constraint gives them nothing to overflow. And the close control reaches the header through `DayDetail`'s `action` slot rather than being positioned over the popup, which is also why the panel — passing no action — lays out exactly as it did before the slot existed. It is deliberately **not** a `ChromeButton`: that component owns `h-header` for controls sitting in a chrome row. And **`<tbody>` is keyed on the month index**: adjacent six-week grids share week keys (for a Sunday start, September 2026 runs `08-30…10-04` and October runs `09-27…11-01`), so React reused those `<tr>`s and their overlapping `<td key="2026-09-30">`, the per-cell `Popover.Root` was never unmounted, and an open popup survived a month step onto a greyed padding cell while the header read OCTOBER — the exact state `activeDay` guards the panel against. **That remount is also the month transition**: the incoming `<tbody>` is a `motion.tbody` that enters 40px off-centre — from the right stepping forward, from the left stepping back — and fades in over 0.35s, so the grid says which way the month moved. It is deliberately **enter-only, with no `AnimatePresence`**: two `<tbody>` elements cannot overlap (they stack), and keeping the outgoing one mounted is the reused-cell bug above, so a full-width push would leave the space it came from empty for most of the animation and a nudge beside the fade carries the direction just as well. Three things it depends on. `transform` on a `table-row-group` (verified: a `translateX` moves the cells and the `<thead>` stays put, collapsed borders intact). `overflow-x-clip` on the view's wrapper, or the offset widens the document and grows a horizontal scrollbar for the length of the animation — `clip` rather than `hidden`, which on one axis forces the other to `auto` and would make that a scroll container; the day popup is portalled and a cell's focus ring is `ring-inset`, so neither is trimmed. And the direction comes from the month **delta**, not from whichever control moved it: the arrows are not the only writer, since `selectDay` moves the calendar when a phone visitor taps a padding cell from another month, and the list view's arrows can jump several months at once. It starts at zero, so the mount that puts this view on screen fades without moving. Reduced motion drops the offset and keeps the fade, read through `usePrefersReducedMotion` rather than Motion's own one-shot snapshot. Only days with events are focusable, which is also what keeps a month from costing 42 tab stops.
- **One gate decides whether an event may show a time**: `resolveEventDateStatus()` in `event-status.ts`, used by the two `/events` views, the event page and the home-page ticket. It answers `{ isFirm, label }` from ONE read, which is what stops a caller pairing the two halves wrongly. Two things live in it. It **`stegaClean`s before comparing** — `dateStatus` is a discriminator crossing from GROQ into JS as a string, and `filterDefault`'s denylist covers `status` but not `dateStatus`, so in draft mode a raw `=== 'confirmed'` is false for every event and each one renders its status word where its start time belongs, silently and only for editors (the rule `SizeChartTable` states: clean wherever a value is COMPARED rather than rendered). And it takes the **events dictionary slice as an argument** (`t`) rather than importing it — which is also why it is a leaf module and deliberately NOT part of `dictionary.ts`, imported for values by fifteen client components including the cart chrome, while `@sanity/client/stega` is not a leaf. The `label` is never the raw enum: those are schema tokens, so rendering one printed an English word on the Chinese page and made the `tba` entry unreachable, since a set value is always truthy.
- **A stored `richDate.timezone` reaches `Intl` only through `resolveEventTimezone()`** (`event-date.ts`), never as `value.timezone || FALLBACK_TIMEZONE`. `Intl` throws a `RangeError` on any zone it does not recognise, and the five readers that format or bucket a date all run during render — so ONE bad value took the whole `/events` page to its error boundary instead of spoiling the row it belongs to. Two unrelated things produce one. The narrow case is a value that was never IANA (`GMT+8`, `Taipei`, `UTC+08:00`, from a hand-edit or an import). The broad one **was draft mode, and is fixed at its source**: `timezone` is not on `filterDefault`'s denylist (it lists `status`) and is neither date-like nor URL-like, so the Presentation tool encoded invisible characters into it for _every_ event and `/events` crashed there on any dataset. The stega `filter` in `sanity/lib/client.ts` now opts `timezone` out — and since `defineLive` shares that client, that one arm covers draft mode too. **Prefer that filter to a per-read `stegaClean` whenever a field is consumed rather than rendered**; the resolver keeps its clean only as a backstop, because a change to the filter would then resolve a Los Angeles event in Taipei rather than crash, which is the worse failure. That is also why it cleans BEFORE judging validity. Validity is whatever `Intl` accepts rather than a curated list, which would reject the valid `Etc/GMT-8` and a bare `UTC`; the answer is memoised on the _cleaned_ string, because constructing a `DateTimeFormat` costs ~65µs, the calendar resolves this a few hundred times per render, and keying on the raw value would store one entry per encoded field per document.
- **The event queries carry no transition tails**, and since the product merge completed the product queries carry none either — see the note at the end of the product section below. Events were migrated in the same deploy as the code (by a one-shot merge script, since removed), so there was never a window where old-shape event documents met new-shape queries.
- **A one-shot script that must see drafts creates its Sanity client with `perspective: 'raw'`**, so drafts appear as `drafts.*` ids — under the client's default (`drafts`) perspective a draft is overlaid onto the published id, so a "publish or discard your drafts first" guard silently passes while the script reads draft content instead of published. The event merge learned this the hard way.

**The product family (`pProduct`, `pProductCollection`, `pProductCategory`) is FIELD-level localized** — one document per product carries every language, mirroring Shopify's one-entity model. Prose lives in `internationalizedArray`s (including `internationalizedArrayPortableTextSimple`, registered via `fieldTypes` in `sanity.config.ts`); everything locale-invariant (Shopify handle, price, refs, images, `soldOut`) exists once, and references to products never involve a language choice. Consequences that differ from the doc-level types: a product's translated-ness is signalled by `title[].language` (drives visibility — a zh-only product is hidden from `en` listings and 404s on the `en` route — plus hreflang via `availableLocales` and the sitemap `locales` projection); slugs are validated with `isUniqueAcrossType` because the default check silently passes when there is no `language` field; the Studio shows one language at a time via the plugin's built-in `languageFilter` (the "Showing 1/2" control is `@sanity/language-filter`, registered automatically because `sanity.config.ts` passes `languageFilter.documentTypes`, derived from `FIELD_LEVEL_I18N_TYPES`; the selection persists per browser in `localStorage`). That config also sets **`buttonAddAll: false`** — with the filter narrowed, the plugin's "Add missing languages" button appears and does nothing, because it decides visibility from the unfiltered item count but only ever adds _visible_ languages. The per-language `en`/`zh_tw` chips beside it do the same job correctly. **Both datasets are fully migrated**, so the `select(defined(language) => …)` transition tails have been removed from `queries.ts`: the product projections now read the merged shape only. `defined(language)` survives in that file solely for the DOCUMENT-level types — `byLocale`, `availableLocalesField`, `pGeneral`, and the `pProductIndex` arm of `SITEMAP_PRODUCTS_QUERY` — so don't read a stray `language` check there as leftover product scaffolding. Note `pProductIndex` is document-level and is NOT part of this family.

**GROQ queries** are centralized in `src/sanity/lib/queries.ts` using `defineQuery()` from `next-sanity`. Composed from reusable fragments: `baseFields`, `linkFields`, `menuFields`, `imageMetaFields`, `imageBlockMetaFields`, `callToActionFields`, `portableTextContentFields`, `freeformField`, `faqBlockField`, `gFaqItemFields`, `gSizeChartFields`, `pageModuleFields`, `formField`.

**Data fetching** uses `sanityFetch` from `src/sanity/lib/live.ts` (wraps `defineLive` from `next-sanity`). Usage pattern in pages:

```ts
const { data } = await sanityFetch({ query: someQuery, tags: ['docType'] });
```

**Visual Editing / Draft Mode** is enabled via Sanity Presentation Tool. The presentation resolver at `src/sanity/lib/presentation-resolver.ts` maps routes to Sanity document types. Three components render in draft mode and they do **not** all sit on the same side of the RSC boundary — getting that wrong is what took Presentation down with _"defineLive can only be used in React Server Components"_:

- **`<SanityLive>` is an async Server Component** — `next-sanity`'s `./live` export is conditional (`react-server` resolves the real module, `default` a stub that only throws), and it awaits `draftMode()`/`cookies()` before rendering its own client half with the `browserToken`. So it renders from `layout/HtmlShell.tsx`, never from a `'use client'` module. `src/sanity/lib/live.ts` carries `import 'server-only'` so a client import fails the build, naming the boundary, rather than throwing in the browser.
- **`<VisualEditing />` and `<DraftModeToast />` are client components** behind the `lazy()` gate in `DraftModeTools.tsx` → `DraftModeToolsInner.tsx`. What the gate needs is to sit in a **client module** — a client reference held by the server tree is listed in the route's client manifest and loads with the page, so gating from `HtmlShell` defers execution but not the download. `React.lazy` is not the requirement, and `DraftModeTools` is the odd one out for using it: the four `*Lazy.tsx` wrappers do the same job with `next/dynamic` inside a `'use client'` file (see the `LocationCurrentTime` note below) and get `loading`/`ssr` with it. Two separate measurements live in those files and should not be conflated — `DraftModeTools.tsx` has ~23KB transferred for the `next/dynamic`-in-HtmlShell shape, `DraftModeToolsInner.tsx` has 78KB raw / ~24KB transferred for the fully-static shape.
- **`<VisualEditing />` and `<DraftModeToast />` are gated on `isDraftModeEnabled`; `<SanityLive>` is NOT.** It renders for every visitor and takes `includeDrafts={isDraftModeEnabled}`, which is what delivers published live updates to anonymous tabs. It used to be gated too, because rendering it for anonymous visitors on Next 16 + next-sanity 12 caused a prefetch/revalidate cascade (4–10x request overage) — fixed upstream in v13, which this repo is now on. `includeDrafts` is the surviving half of that gate: everyone subscribes, only a draft session receives unpublished content. It is _not_ about Dynamic APIs: `draftMode()` does not opt a subtree out of SSG, and `SanityLive` reaches `cookies()` only in draft mode — but so does `sanityFetch`, on every page, so that could never have been the reason. Published freshness comes from `/api/revalidate-tag` **while nobody is editing**: whenever `SanityLive` is mounted, next-sanity's `revalidateSyncTags` Server Action expires shared `sanity:*` tags on every live event, so an open Presentation session also invalidates prerendered pages for anonymous traffic.

### Page Architecture

Each page route follows this pattern:

1. Server component in `src/app/(frontend)/[route]/page.tsx` — fetches data via `sanityFetch`
2. `generateMetadata()` — fetches data with `stega: false` for clean metadata
3. `generateStaticParams()` — for dynamic slug routes, fetches all slugs at build time
4. Render delegates to a `_components/Page*.tsx` client or server component

Every route lives under `/[locale]/(site)/` except `/events-crew` and `/email-signature`, which sit outside the locale segment and therefore have no `$locale` to resolve against, and `/module-preview/[locale]/[type]` — the Studio picker's preview frames (see PageModules below), a separate root layout with its own locale segment that `src/proxy.ts` skips entirely. `[...rest]` is a catch-all inside `(site)` that renders the localized 404 inline — `notFound()` can't render a styled boundary here.

**Site-wide data** (`siteDataQuery`) is fetched once per request via `getCachedSiteData` (`src/sanity/lib/siteData.ts`). `HtmlShell` (a Server Component) receives the full result; the client `<Layout>` receives only the `pickLayoutData()` slice — header, footer, newsletter, mobileMenu, toolbar, cart, siteTitle — because everything handed to `<Layout>` is serialized into every page's RSC payload. `announcement`, the rest of `sharing`, `consent`, `integrations` and `productSubmissionEmail` deliberately do not cross that boundary (the last three are consumed server-side or passed separately by `HtmlShell`).

**Every page under `[locale]` is prerendered (SSG), and one careless line takes them all back out.** A dynamic API anywhere in a layout opts its whole subtree out of static generation, so `[locale]/layout.tsx` must not call `cookies()`, `headers()` or `connection()` — a single `cookies()` there, reading the consent decision, was what kept all ~380 pages server-rendered on demand. Freshness comes from tags instead: `sanityFetch` already sets `revalidate: false` plus tags, so `/api/revalidate-tag` and `/api/shopify/revalidate` invalidate the prerendered HTML, not just the Data Cache. Two consequences worth knowing: the Shopify webhooks stop being optional (a missed one freezes a price in HTML until the next deploy), and `router.refresh()` is no longer a way to make the server re-decide anything — on a prerendered route it re-fetches the same cached payload. What stays dynamic, correctly: `[...rest]` (the 404 catch-all), and `products/all` + `events-crew` (both read `searchParams`).

**Four routes carry `export const revalidate = 3600`** — `/`, `/[slug]`, `/events` and `/events/[slug]` — because an `eventsBlock` (and the events listing) decides what to render from the wall clock, which no content edit invalidates: without it the prerendered HTML keeps listing events that ended months ago. That is still SSG with ISR, not dynamic rendering, and it composes with the content tags rather than replacing them. It does **not** cap the deliberate no-TTL Shopify fetches — Next takes the minimum only across _lower_ fetch revalidates, and `false` is infinite, not lower. The cost is scope: every `pGeneral` page is hourly-ISR even when it carries no events module, because a segment revalidate must be a static literal and cannot be derived from page content; regeneration is lazy, on the next request. `use cache` + `cacheLife` would be the per-module answer; next-sanity 13 unblocked the Sanity half of it, but the wall-clock reads still do (see the note in `next.config.mjs`). Do not reach for a client-side clock instead — that corrects the view after hydration, which is the divergence the routing section above catalogues.

**Cookie consent is read in the browser, never on the server** — that is the whole reason the above holds. `useConsent` (`src/hooks/useConsent.ts`) is a `useSyncExternalStore` over the `bw_consent` cookie with three states: `undefined` (not read yet — the server snapshot), `null` (no decision, prompt), or the decision. Both `ConsentBanner` and `HeadTrackingCode` read it, so prerendered HTML carries neither the banner nor any tracking script, and a returning visitor sees no banner flash. Writers call `writeConsentClient` then dispatch `CONSENT_CHANGED_EVENT`; everything else follows from the re-read. `HeadTrackingCode` is the only thing that talks to gtag, which is what keeps Consent Mode's one-`default`-before-any-`update` ordering a local invariant rather than a race — do not push consent signals from the banner as well.

**The visual system lives in `DESIGN.md`, which is canonical for it.** Entrance animations (`reveal`, `.animate-page-in`, and why they are CSS and not JS), the nine-rung `t-*` type ladder, and the interaction-state vocabulary with its four traps all moved there. Read it before any UI work.

### Routing

`src/lib/routes.ts` is the single source of truth for document type → URL resolution. `DOCUMENT_ROUTES` drives both `resolveHref()` and `buildResolvedHrefGroq()`, which `scripts/generate-groq-constants.mjs` materialises into `src/sanity/lib/groq-constants.generated.ts` for queries to interpolate — TypeGen cannot evaluate a function call, so the query side needs a plain string literal. Regenerate with `npm run generate:groq` (also run by `predev`, `prebuild` and `typegen`); `groq-constants.test.ts` and CI both fail when it is stale.

**`usePathname()` is not the same string at build time and in the browser, and route predicates must normalize for that.** `proxy.ts` rewrites the public `/products/x` onto the internal `/en/products/x`, and `generateStaticParams` prerenders that internal path — so a prerender sees the `/en` prefix and the client router never does. Any predicate that compares a `usePathname()` value therefore has to strip **every** locale prefix, the default included, or the build bakes one answer into the HTML and JS visibly corrects it after hydration. That is what shipped `/products` and `/size-guide` dark before flipping them to light, hid the `/newsletter` newsletter block only after hydration, left nav active-state out of every prerendered page, and put a broken `/zh_tw/en/...` language-switcher href on all 182 English pages. The split lives in `src/lib/i18n.ts`: **`stripLocaleFromPathname` for anything out of `usePathname()`, `stripLocaleFromHref` for an authored or resolved link target** — the two differ only on the default prefix, which is exactly where the mistake is invisible, since in an href `/en/...` is a real path segment (a `pGeneral` page slugged `en`) that must survive. `src/lib/routes.ts` wraps them as `normalizeRoutePath` / `normalizeHrefPath`; `checkIfLinkIsActive` needs one of each, because it compares a pathname against an href. Regression tests are in `src/lib/routes.test.ts`.

**Adding a routable page type touches three hand-maintained lists** — `DOCUMENT_ROUTES` in `routes.ts` (the GROQ arm is now DERIVED from it, so that half no longer drifts; mark a route with no backing document `synthetic: true` and it is excluded), plus `internalLink.to[]` in `schemaTypes/objects/link.ts` and `pageDocumentOrder` in `schemaTypes/components/LinkObject.tsx`. Miss either of the last two and the page never appears in the Studio link picker, so editors cannot add it to a menu or CTA and the `resolvedHrefGroq` case is dead. Also add the type to `SITEMAP_PAGES_QUERY` and `presentation-resolver.ts`.

### PageModules System

`src/components/PageModules.tsx` is a switch-based renderer that maps Sanity `_type` values to React components: `freeform` → `<Freeform>`, `faqBlock` → `<FaqBlock>`, `eventsBlock` → `<EventsBlock>`, `heroBlock` → `<HeroBlock>`, `productsBlock` → `<ProductsBlock>`. All five are available on `pHome.pageModules` and `pGeneral.pageModules` — those are the only two `pageModules` arrays, so a new type must be added to **both** `of: []` lists. `PageModules` also takes a `locale`, threaded from `PageHome`/`PageGeneral`: `EventsBlock` and `ProductsBlock` are Server Components that resolve dictionary strings and Shopify prices server-side, so they cannot read `LocaleProvider`'s client context. It also takes `headingLevel`, which only `heroBlock` reads — `PageHome` passes `'h1'` for the module in slot 0 because nothing above it claims the page's heading, while `PageGeneral` renders its own `<h1>` and leaves it at the `'h2'` default. Slot 0 is decided by **position, not content**: nothing inspects the modules to find the one that deserves the heading, and because hidden modules are filtered out in GROQ, slot 0 is the first module a visitor actually sees. The cost, accepted deliberately: only `heroBlock` reads `headingLevel`, so **the homepage has no `<h1>` at all when slot 0 is any other module type, or a hero with no heading** — the page reflects the module order as authored rather than guaranteeing a heading.

Adding a module type touches: a schema object under `schemaTypes/objects/`, the import + array entry in `schemaTypes/index.ts`, both `of: []` lists, a fragment plus a `_type ==` arm in `pageModuleFields`, a `case` in `PageModules.tsx`, `components: pageModuleComponents` **and** `pageModuleHidden()` in `fields` on the object type (the visibility pair below — half of it is worse than neither), `moduleRule()` around any `Rule.custom` the type adds, a preset in `src/app/module-preview/_presets.ts`, and `npm run typegen`. Use the `pageModuleComponents` spelling literally: `page-module.test.ts` discovers which files are page modules by matching that exact registration string, so a type registered any other way is invisible to the guard that checks the `moduleRule()` wrapping. Nothing type-checks the switch — `module` is `any` — so a missing case renders blank rather than failing the build.

**The Studio's "Add item" is a visual picker, not Sanity's dropdown.** `schemaTypes/components/PageModulesInput.tsx` is the `components.input` on both `pageModules` arrays; it swaps only `arrayFunctions` through `renderDefault`, so reorder, the edit dialog and the eye toggle stay Sanity's. Each card is a scaled-down iframe of `/module-preview/{locale}/{type}`, the locale being the edited document's `language` — its own root layout (fonts, `globals.css`, the theme class read off `isLightThemePath` without mounting next-themes, `LocaleProvider`; no chrome, no `SanityLive`, `<body inert>`) rendering the real `PageModules` from `_presets.ts`, so a card cannot drift from the site. Every locale × type is prerendered with hourly ISR (the `eventsBlock` wall-clock reason) — which editors carrying the draft-mode cookie bypass, so theirs render on demand with draft events. The path is excluded from `src/proxy.ts`'s matcher as `module-preview(?:/|$)` — anchored, so a page slugged `module-previews` still gets its locale rewrite (otherwise the preview is rewritten under `/en` and falls into `[locale]`), and the layout's `noindex` keeps it out of search — deliberately not a `robots.ts` disallow, which would stop crawlers from ever reading that `noindex`. The presets carry no asset refs, so every card renders on any dataset, and the hero preset is deliberately not the wave — its CPU shader never pauses inside the frame and shares the Studio's main thread; `eventsBlock` still fetches its own events, so its card is blank when the dataset has none upcoming. `page-module.test.ts` fails when a host array's member has no preset (a 404 card), or when a preset's data trips its module's own empty-data bail (a blank card).

**Per-module visibility is a `hidden` boolean toggled by an eye button on the array row** — `schemaTypes/components/PageModuleItem.tsx` exports **two** Studio components, bundled as `pageModuleComponents` and registered together on all five module types (so they cover both `pageModules` arrays without either array knowing); the field they write is `pageModuleHidden()` in `schemaTypes/objects/page-module.ts`. Two components because the halves live apart: `components.item` is the only place with `inputProps.onChange` and the item's value, while `components.preview` is the only one that renders _inside_ the row. **The eye lives in the item, and gets into the row's trailing control cluster by `createPortal`** — the item finds the cluster at runtime by querying its own subtree for `[data-testid="array-item-menu-button"]` and taking `.closest('[data-ui="Flex"]')`. `renderDefault` is still called, so nothing native is re-owned: insert before/after, the error marker for a nested field, `regenerateKeys` for duplicate/copy, the max-reached guard and the edit dialog all stay Sanity's — which is the point, because `useInsertMenuMenuItems`, `useChildValidation`, `regenerateKeys` and `useArrayValidation` are all unexported, so rebuilding the row would have cost all four. **This depends on Studio-internal DOM**, so a Sanity upgrade can move the anchor; when it is not found the item passes the toggle down through a React context and `components.preview` renders it into `DefaultPreview`'s `status` slot instead — a placement regression rather than a missing control. Read-only rows always take that fallback (Sanity nulls `menu` for them) and show a state indicator rather than a control. So registering only `item` keeps the eye on editable rows but loses the read-only indicator and that fallback. Two details worth knowing before touching it: use `.closest`, never `.parentElement` (Sanity's internal Button wraps itself in a tooltip `<span>`, and `ContextMenuButton` always sets `tooltipProps`), and scope the query to the row, never `document.getElementById` (form ids are the item's path and are namespaced by neither pane nor document, so a document open beside its duplicate resolves both rows to the first match). The pair is why editors can park a section instead of deleting it, which is the only thing the Studio otherwise offers and which throws the module's content away. Absent means visible — nothing needed backfilling, and the GROQ side must therefore `coalesce`, since `hidden == false` and `!hidden` each drop every untouched module. `moduleVisible` in `queries.ts` is applied as the array **predicate**, not projected as a field, so a switched-off module never reaches JS: that is what makes `PageHome`'s slot-0 `<h1>` land on the first module a visitor actually sees, keeps a hidden `faqBlock` out of the FAQPage JSON-LD, and stops `EventsBlock`/`ProductsBlock` running their own fetches. It also means a module's own validation must not block publishing while it is off, so **every `Rule.custom` on a module field is wrapped in `moduleRule()`** (`schemaTypes/objects/page-module.ts`), which clears the error when the host module is hidden. A wrapper rather than a condition pasted into each rule because the exemption is one invariant across five files and hand-editing each site is how you miss one — `eventsBlock`'s two CTA rules were missed exactly that way; `page-module.test.ts` now fails when a `Rule.custom` is unwrapped. `Rule.unique()` is deliberately left alone: a duplicate reference is a data error, not an unfinished section. The exemption is narrower than "a parked module never blocks publishing", though — `moduleRule()` can only wrap a `Rule.custom`, so `Rule.required()`/`min`/`max`/`regex` on a module field, and validators on the shared objects a module renders (`section-appearance`, `custom-image`, `call-to-action`, `link`), bypass it and are invisible to the guard. Of those, `call-to-action` carries `Rule.required()` on its `link` field, so de-duplicating heroBlock's and eventsBlock's inline CTAs through that factory would reintroduce the bug; the other three carry none. Prefer a `Rule.custom` through the wrapper over `Rule.required()` on a module field. It is deliberately **not** part of `sectionAppearance` — visibility is not appearance, and `SectionShell` never sees it. The cost to accept: a hidden module is also gone from the Presentation preview, which is correct, since the preview should match the site.

**Every module renders through `<SectionShell>`** (`src/components/SectionShell.tsx`) — the one place `sectionAppearance` becomes classes and styles. Three things there are load-bearing and look like tidy-ups waiting to happen:

The three load-bearing details — why the authored colours are applied as _token_ overrides rather than as `color`/`background-color`, why spacing is four custom properties rather than generated class names, and why the horizontal inset is a published `--section-inset` custom property rather than a class (pairing the centring `p-x-max` with a `max-w-*` collapses the section at wide viewports, and a full-bleed module's carousel cannot read a class on its ancestor) — are in **DESIGN.md (§Sections)**.

`FaqBlock` renders its heading inside its own `wysiwyg` children rather than through the shell's `heading` prop, so it keeps its prose styling; it also defaults `maxWidth` to `'m'` for blocks authored before `sectionAppearance` gained its `initialValue`.

**`pageModuleFields` sits low in `queries.ts` on purpose.** It interpolates `productCardFields`, `titleVisible` and `visibleProducts`, and every fragment in that file is evaluated at module init, so moving it back up beside `freeformField`/`faqBlockField` is a use-before-declare the compiler rejects (TS2448).

**Do not hoist the repeated `sectionAppearance` projection into its own fragment.** All five module fragments spell it out verbatim, and that is load-bearing: one more level of interpolation on a chain that already reaches `portableTextContentFields` → `linkFields` → `resolvedHrefGroq` makes the Sanity query extractor die with _"Maximum call stack size exceeded"_ on `pageHomeQuery` and `pageGeneralQuery` alone. Those two lose their generated result types while every other query still resolves, so `npm run typegen` still reports success — read the error line above its summary, not just the summary. The shared cache tags are exported as `PAGE_MODULE_TAGS` instead, which is the part that actually drifts. The same rule now covers the `callToAction{ label, link { … } }` projection, spelled out verbatim in `heroBlockField`, `eventsBlockField` and `page404Query`: those are siblings at equal depth, which is safe, whereas hoisting them into one fragment adds the level that breaks the extractor. `eventsBlock`'s copy carries the warning inline.

**`eventsBlock` picks its own events** — the editor chooses a time window (next 7 days / next 30 days / all upcoming) and a count, never individual events. It also **fetches them itself** (`upcomingEventsQuery`, via its own `cache()`d `sanityFetch`) rather than through the page query: those events are not a dereference of anything the page holds, and nesting them there put `$upcomingFrom` on every `pGeneral` page's cache key and the three event tags on every `pGeneral` page's fetch. `productsBlock` is the opposite case and correctly stays in the page query — its products _are_ fields on the module. The `$upcomingFrom` bound is only a payload guard, deliberately a day slack; `selectUpcomingEvents()` in `src/lib/event-date.ts` makes the real cut, because "has this ended?" needs the event's timezone and an end-of-day fallback that GROQ cannot express. The window itself is resolved to a **number** (`windowDays`) inside GROQ, so no discriminator crosses into JS as a string and nothing needs `stegaClean` — the same reason `faqBlock.source` and `productsBlock.source` stay in GROQ. An empty window renders nothing at all, heading included; the schema description says so. It renders the events as **square tickets in an embla carousel**: `EventsBlock` stays a Server Component and the tickets are server-rendered, with the thin client `<EventsCarousel>` wrapper owning only the reduced-motion decision (embla animates with JS transforms, so a CSS media query cannot reach it). No image is projected — `eventCardFields` is shared with `pEventsQuery`, and the ticket is deliberately typographic.

**`productsBlock` renders `<ProductCard>` with live Shopify prices**, fetched by the module itself (`withLiveCardPrices`, which wraps `getCardCommerce` + `applyCardPrices` — the `ProductRelatedGrid` pattern). It never passes `priority` — the host page owns the single LCP image.

**`heroBlock` is the page opener** — eyebrow, heading, paragraph, optional background image and CTA. It is where the homepage heading lives now: `pHome.landingTitle` was a bare string rendered above the modules by `PageHome`, so the one page most needing a designed opener was the one whose opener could not be edited or moved. Both datasets have been migrated off it, and the field, its `pageHomeQuery` projection and the `PageHome` build guard that caught an unmigrated dataset have all been retired, so `PageHome` renders nothing but its modules. Entrance is the `reveal` utility, not Motion, for the reason the animation note above gives — a Motion mount animation on the page's own `<h1>` strands it at `opacity: 0` if JS never runs. **`backgroundEffect: 'wave'` swaps the background image for `<HeroWave>`** (`src/components/ui/HeroWave.tsx`), a per-pixel CPU canvas shader and the only `<canvas>` and rAF loop in the codebase. It reaches `HeroBlock` only through `HeroWaveLazy.tsx`, a `'use client'` `next/dynamic` wrapper on the `LocationCurrentTimeLazy` model, because **`next/dynamic` called from a Server Component does not code-split on the client** — measured on a production build, a `dynamic()` inside `HeroBlock` itself left the canvas code folded into the homepage and `/[slug]` route chunks, shipped to the zh_tw homepage and `/en/about` alike. Keep the wrapper the sole route to `ui/HeroWave`; it passes `loading` (without it `next/dynamic` renders no Suspense boundary and the chunk gates hydration) and wraps the canvas in an error boundary that renders nothing. The option is resolved to a boolean in GROQ (`waveBackground`) so no stega-encoded string is compared in JS; the canvas paints one still frame under reduced motion and stops its loop while scrolled out of view. It replaces the image rather than layering over it — the shader writes alpha 255 everywhere — so the schema hides the image field while it is selected. Its colours are fixed in the component, not editable — monochrome by brand (the tokens are achromatic), every knob a named constant at the top of `HeroWave.tsx`. Reduced motion is read through `usePrefersReducedMotion` (`src/hooks/`), which subscribes to the media query; Motion's `useReducedMotion` is a one-shot snapshot and never re-renders on an OS toggle. **When the wave hero opens the page it runs under the site header**: the header is `position: fixed`, so it takes no layout space and the hero simply starts at the top of the viewport. `<Main>` carries the space every other page needs and `body:has([data-hero-underlay]) main` in `globals.css` drops it here, so no negative margin is involved (the padding is declared on the `main` rule itself, not as a class on `<Main>` — the note there says why). `HeroBlock` marks the wave wrapper `data-hero-underlay`, opens at `min-h-[calc(90svh-var(--height-g-toolbar))]` / `lg:min-h-[90svh]` instead of its usual `min-h-main` — the SMALL viewport, since `vh` overflows the visible area while mobile browser chrome is expanded, less the toolbar strip below `lg` where `ToolBar` is `fixed bottom-0` — and gives the copy `mt-header-space-0` so it stays centred below the header. This replaced a `-mt-[calc(var(--height-header)+…)]` on the section, which worked only by collapsing its margin **through** `<main>` — nothing there to stop it — and so moved `<main>`'s own box, meaning any padding later added to `<main>` would have killed the overlap silently. The header's background has one home, the `[data-site-header]` rules in `globals.css`, as a function of `--header-progress` — registered with `@property` (`inherits: false`), 1 everywhere so the header is its usual 95% paper plus `blur-xs`, and 0 under a marked hero via `body:has()`, so the first paint is already transparent with no post-hydration flip. The header's class list carries no `bg-*` or `backdrop-*` utility, which is what lets those rules live in `@layer components`. `HeroUnderlay` (`src/components/HeroUnderlay.tsx`), the wave hero's wrapper when it opens the page, owns the progress: it measures once and on resize, writes deduplicated progress inline on scroll, sets `data-header-solid` at progress 1, and attaches and detaches with the hero — so a hero that appears or disappears without a route change (draft-mode live updates re-render the page in place) stays in step, which a pathname-keyed effect in the Header could not. The header is fully solid once `HEADER_SOLID_AT` of the hero has scrolled past; the range is floored at 1 and capped to the reachable scroll so a short page still gets there. A wave hero hands the resolver a near-black paper (`WAVE_PAPER`) so ink comes out light whatever background was authored. **The underlap is no longer conditional on the authored max width**: `sectionAppearance.maxWidth` caps the hero's COPY COLUMN and never its `<section>`, so the canvas always reaches edge to edge and a capped wave hero still underlaps — see DESIGN.md §Sections for that split and why no other module needs it. The gate is now `waveBackground && headingLevel === 'h1'`, and do NOT swap that for `isPageOpener`, which looks like the more honest signal and is not: the CSS hooks match `body:has([data-hero-underlay])` anywhere in the body, and `PageGeneral` renders its own `<h1>` above its modules while still passing `isPageOpener` to slot 0, so a hero there would pull the page title under the header. The blur is a step switched on by that attribute, not a ramp: a backdrop blur over the animating canvas re-blurs on every wave frame, so it stays `none` until the paper is solid enough to hide the switch. Wave only: an image hero's colours are the editor's, so header ink has no guaranteed contrast over it. The canvas itself carries `mask-b-from-60%`, dissolving over its bottom 40% into whatever the section paints beneath so the hero has no hard bottom edge — a mask rather than a gradient overlay, so no colour is assumed, tuned beside `DEPTH` in `HeroWave.tsx`.

### SEO & Structured Data

- **Metadata** comes from each doc's `sharing` fields via `src/lib/defineMetadata.ts`; site-level metadata (title template, favicons, OG defaults) lives in the root layout.
- **JSON-LD** is injected via `<JsonLd>`, with per-schema builders in `src/lib/define*JsonLd.ts`. **It must be built from `stegaClean`-ed data** so draft mode doesn't leak stega characters into the markup. `<JsonLd>` is a **Server Component that renders the `<script>` inline** (so the blocks sit in `<body>`, not `<head>`, and they follow client-side navigation). It deliberately does **not** use `useServerInsertedHTML` — worth knowing before reaching for that API for anything else, e.g. a theme or analytics tag: Next invokes every registered callback on every flush of the stream, so a callback that returns markup unconditionally emits it once per flush (this cost 15,173 script tags across the prerendered site before it was caught), and merely registering one disables Next's empty-callback fast path, making every flush run a full render to produce an empty string. Use `collectFaqItems()` to pull FAQ items out of `faqBlock` modules — it matches on `_type === 'faqBlock'`, a runtime string, so renaming the module type without it silently drops the markup.
- **Sitemap and robots are dynamic**, so `SITE_URL` must be set or absolute URLs break. `robots.ts` deliberately allows AI/answer-engine crawlers.
- **There are three sitemaps, not one.** `app/sitemap.ts` uses `generateSitemaps()`, so it serves `/sitemap/pages.xml`, `/sitemap/events.xml` and `/sitemap/products.xml`; `app/sitemap_index.xml/route.ts` is the index that lists them. The ids live once in `src/lib/sitemaps.ts` (`SITEMAP_IDS`) and key the `QUERIES`/`SITEMAP_TAGS` records, so adding a sitemap is a compile error until every map has it. **Every routable type must reach a sitemap**, and `src/lib/sitemaps.test.ts` fails if one does not: page types come from the queries' `_type in [...]` lists, while the three synthetic `/products/*` indexes have no document for a query to find and are emitted from `SYNTHETIC_PRODUCT_ROUTES` (their lastmod is the newest of whatever they list). Entries carry no `priority` or `changeFrequency` — Google ignores both — and the index carries no `<lastmod>`, because the only value it could produce cheaply is "now", and lastmod Google finds unreliable is lastmod it ignores sitewide. **`/sitemap_index.xml` is the canonical sitemap URL** — `robots.ts` advertises it and it is the one to submit — and **`/sitemap.xml` is a `beforeFiles` rewrite onto it** (`next.config.mjs`), so the path crawlers probe first answers **200 `application/xml`**. A route handler at `app/sitemap.xml/route.ts` is impossible, because Next reserves that path for `app/sitemap.ts` even under `generateSitemaps()` and fails the build with _"Conflicting route and metadata"_, so config is the only way to claim it. Do not submit both to Search Console: they serve the same index, and two rows split the per-section coverage the three-way split exists to give. It **was** a 308 until 2026-09-15; the Search Console row that prompted the change read "General HTTP error, **302**", which nothing in this repo can emit (the entry was `permanent: true`), so the redirect was probably never the cause and an apex→www or http→https hop at the domain layer is the better suspect — **if that error returns against `/sitemap_index.xml`, look there, not here.** The rewrite's real value is removing the redirect from the question. Two mechanics to keep straight. `/sitemap.xml` must **not** also appear in `redirects()`: the order is headers → redirects → middleware → `beforeFiles`, so a redirect on the same source silently makes the rewrite dead code — `src/lib/sitemaps.test.ts` asserts both halves. And `/sitemap` and `/sitemap_index` must stay **redirects** for the mirror-image reason: middleware runs _before_ `beforeFiles`, so `src/proxy.ts` (whose matcher skips dotted paths but not these) has already prefixed them with the default locale, a `/sitemap` rewrite source no longer matches, and each falls to `[...rest]`'s soft-**200 HTML** — verified by trying it, and exactly what Search Console reports as "your sitemap appears to be an HTML page". The dotted `/sitemap.xml` is not unrouted either: `/[locale]` matches it and hard-404s on the invalid locale.
- **`lastmod` comes from `contentUpdatedAt`, not `_updatedAt` alone.** A page document's timestamp does not move when the documents it renders do, so each sitemap query projects a `contentUpdatedAt` array of its referenced `_updatedAt`s and `lastModifiedFor()` takes the newest. Two rules: whatever a query dereferences must also appear in that sitemap's `SITEMAP_TAGS` (the fetch is `revalidate: false`, and the webhook only revalidates the changed doc's own `_type`, so an untagged type freezes the sitemap forever) — `src/lib/sitemaps.test.ts` enforces this mechanically and fails on any unmapped `->`; and the projection must mirror the _render_ path's conditions, e.g. `faqBlockUsesSet` matches `faqBlockField`'s `select()` so an orphaned `questions[]` array on a set-backed module cannot bump lastmod, and `moduleVisible` matches the page queries' array predicate so a switched-off module's FAQ set cannot either. Deliberately excluded: list membership and site-wide colors, which would bump every sibling page on one edit.
- **FAQ system**: three layers, each owning one thing. Author a question once in `gFaq` (Global → FAQ) — it carries both languages. Group questions into an ordered **set** in `gFaqList` (Global → FAQ Sets). Then point something at that set: `pFaq.faqSet` renders it at `/faq`, and a `faqBlock` page module renders it on `pHome`/`pGeneral` with its own heading and appearance.
- **`faqBlock` has two sources**, and the difference is the whole point of sets. `source: 'set'` (the default) points at a `gFaqList`, so every page and both languages showing that set stay in step. `source: 'picked'` holds its own `questions[]` array — convenient for a one-off block, but `pHome`/`pGeneral` are document-localized, so that list lives on this page in THIS language and the other language's copy must be curated separately. The field descriptions say so; choose `picked` knowingly. The GROQ `select()` falls back to the set arm, so a module with no `source` renders its set.
- **Why sets exist**: `pFaq`, `pHome` and `pGeneral` are all document-localized, so an inline reference array on any of them is one list **per locale** — the same questions curated twice, drifting apart (the two prod FAQ pages reached the same fifteen questions in different orders). A set carries no locale, so both language versions of a page render one list, and reordering the set moves both at once. The residual gap: which set a page points at is still a per-locale field, so someone can repoint one side — one visible reference rather than fifteen silent array items. `pSizeGuide` still makes the old inline trade with `gSizeChart`.
- **The FAQ migration is complete in both datasets**, so `pFaq.faqSet` is a publish-blocking error rather than the warning it carried through the migration window. (`faqBlock.faqSet` is required only when its `source` is `set`, and conditionally so — a hidden field must never block publishing.)

### Key Shared Components

Most of `src/components/` is self-describing; these carry rules the code alone won't teach you.

- `<SizeChartTable>` — Renders one `gSizeChart` as a table. Exports `isRenderable()` so callers gate empty states on the same condition it bails on (it `stegaClean`s each size — draft mode encodes metadata into `sizes[n]`, so a raw truthiness test calls an empty chart renderable). Uses `border-separate` and a column-count-derived `minWidth` so the label column can pin while values scroll, and marks the scroll container as a focusable `role="region"` so keyboard users can reach clipped columns — see the notes in the file before changing any of these.
- `<WeatherWidget>` — Taipei conditions, and it has **three mount sites, and no two may fire on one page**. The rule is **ownership of a content region, not a route**: whichever component owns the box the widget should sit in mounts it. `<HeroBlock>` pins one inside the page's **first** hero, gated on `ownsWeatherWidget` — which `PageHome`/`PageGeneral` decide once per page (`pageModules.find(m => m._type === 'heroBlock')`) and thread through `PageModules`. Something must choose, because neither `pageModules` array caps how many heroBlocks it accepts and two would poll `/api/weather` on separate schedules showing separate timestamps; it is **ownership, not position**, because gating on slot 0 leaves a `[freeform, heroBlock]` page with no widget at all, and `headingLevel === 'h1'` cannot stand in for it since `PageGeneral` renders its own `<h1>` and passes no level. `PageHome` mounts a `fixed` fallback when no hero owns one — prod's `pHome` documents still have no `pageModules`, so leaving it to the hero left both locales with no widget. And `PageEvents` and `PageEventSingle` each mount their own, **`sticky`**, inside their own page root.
  - **Why those two mount their own rather than taking one from the chrome.** A sticky box is clamped to its CONTAINING BLOCK, so mounting inside the page root makes that root — the list/calendar, the event — the clamp: the widget rides the bottom of the viewport while the section is on screen and then leaves with it. `<Layout>` used to mount this arm `fixed`, which rode over the newsletter and the footer; moving it into `<Main>` instead would clamp it to `<main>`, which still contains the newsletter. There is a bundle reason too, but a small one — measured against a production build, the chrome mount cost every route only the `dynamic()` call plus `WeatherBoundary` (~0.2KB), since the widget body and `@/lib/weather` were already in their own chunk. Directionally right, an order of magnitude smaller than it sounds; don't cite it as the deciding reason.
  - **The route predicate is gone.** `shouldShowWeatherWidget` and `WEATHER_WIDGET_SUBTREES` were deleted with that arm. The failure mode inverted with it: commit `3a81c53` once left the predicate computed-but-unread and silently cost `/events` its widget, whereas now reviving that arm would give every events page **two**. So `src/lib/weather-widget-mounts.test.ts` reads the source of all three mounts AND asserts the two negatives — `layout/index.tsx` must not contain `<WeatherWidget`, and `routes.ts` must not contain `shouldShowWeatherWidget`. **The detail panel sits below the trigger and IN FLOW, so both events mounts go through `<WeatherWidgetRail>` rather than being sticky themselves — that wrapper is load-bearing, not scaffolding.** The trigger is the box's header and the box grows upward off its bottom anchor, which is only safe while the widget is out of the page's flow. A bottom-anchored widget sitting in normal flow is the one arrangement that breaks: measured, opening the panel there grew the document 198px, shoved the newsletter and footer down by the same, and once the widget had settled at its section's end dragged its own bottom edge down 53px. (Making the panel a drop-up instead also fixes it, but puts the rows above the trigger — not the design.) The rail is the sticky element and the widget is a normal in-flow child of it with a FIXED rail height: an over-tall flex item overflows its container's start edge rather than stretching it, so `items-end` pins the widget's bottom while the panel grows past the top and the rail's own box — the only part that is layout — never changes. It owns the sticky offset, `h-11` (44px against a pill of 40–41.5px — `2px border + 20px padding + one line of t-b-2`, that rung clamping `0.75rem→0.8125rem` at line-height 1.5), and `z-g-toolbar`, since `position: sticky` ALWAYS creates a stacking context and would otherwise trap the widget's own z-index below the month bar's `z-10`. Horizontal placement is `justify-end` on the rail, NOT the widget's `right-contain` default, which is inert on an in-flow box — so the gutter is whatever the rail's box gives it: `PageEvents` passes none (its root carries `p-x-max`) and `PageEventSingle` passes `m-x-max` (its root carries none). That is deliberately not a negative margin cancelling a parent's padding; `products/layout.tsx` makes the same call and its comment gives the reason. `PageEventSingle` is a Server Component, which is fine`PageEventSingle` is a Server Component, which is fine and is exactly what `WeatherWidgetLazy` exists for: the `dynamic()` lives inside the `'use client'` wrapper, so the split is real (`<HeroBlock>` is an RSC importing it the same way). Always import from `@/components/WeatherWidgetLazy`, for the reason below.
- `<LocationCurrentTime>` — Live local Taipei time on `/events*`. **Always import it from `@/components/LocationCurrentTimeLazy`**, never from the component file directly: it carries `date-fns` plus both locale bundles, and both render sites (Header, MobileMenu) sit in the always-mounted chrome — one static import anywhere puts that weight back into every route's shared chunk (measured: −61KB with both sites lazy).
- `<ProductCard>` — `src/components/ProductCard.tsx`. Knows nothing of Shopify's schema; `applyCardPrices` rewrites its `price` upstream and hands it two purpose-built fields — `addToCart` (a descriptor, never `ProductCommerce`) and `outOfStock` — which pick one of three footer states: the quick-add control in `ProductCardAddToCart.tsx`, a sold-out line, or the original "View" affordance. Which state a product gets, and why a two-option product deliberately gets none, is in `.claude/rules/shopify-cart.md`. Lived under `products/_components/` until the cart drawer and `productsBlock` both needed it from outside that route.
- `ui/Carousel` — embla, not Base UI, unlike everything else in `ui/`. The product gallery is its only consumer.
- `ui/Tabs` — `TabsTrigger` carries a `cva` variant (`variant="pill"`, with `size` as a separate knob), mirroring `buttonVariants`. Its state selectors are Base UI's `data-active` / `not-data-active` — the Radix `data-[state=active]` spelling fails silently here, leaving the pill unfilled on every route at once. The site's pill tab was a ~200-character class string spelled out verbatim in `/size-guide` and again in `/events`, and the two had already drifted on padding and type scale with nothing recording whether that was deliberate — so a restyle of the active fill or the focus ring would have landed on one page and not the other. The `default` variant is still an unstyled passthrough, so other call sites are unaffected. **The variant itself lives in `ui/tabsTriggerVariants.ts`, a leaf module, not in `Tabs.tsx`** — that file imports `@base-ui/react/tabs`, so importing the variant from it drags the whole tabs runtime into the caller's bundle, which is dead weight for any caller that renders no tabs. Verified against a production build: `/events` (which borrows only the variant) carries no tabs chunk, while `/size-guide` correctly still ships one (~8KB gzip). Same leaf-module reason `dateFnsLocale.ts` is kept out of `i18n.ts`. `/events` borrows the variant for its single view-toggle button rather than restating the pill: a plain button never carries `data-active`, so the `not-data-active:` rules are the ones that match and it renders as the resting outline pill, while the `data-active:` fill can never fire. **Do not fold those `not-data-active:` rules into the unprefixed base** — for a real tab the prefix looks redundant, but removing it silently fills in a button on another route. The note lives on the cva itself, where whoever tidies it will actually be looking.
- **Base UI (`@base-ui/react`) is the primitive layer** under everything else in `ui/` and under `Popover`. Its four idioms — `render` instead of `asChild`, bare state attributes instead of `data-state`, the `z-index` on the `Positioner` rather than the `Popup`, and the Motion overlay handbook — are in **DESIGN.md (§Components)**.

### Utilities (`src/lib/`)

Function-level detail is in the files; these are the non-obvious ones.

- `calendar.ts` — month-grid **geometry** for `/events`' calendar view: `DayKey` (a civil `yyyy-MM-dd` date carrying no timezone), `YearMonth`, the grid, and the month-index algebra. The split from `event-date.ts` is the load-bearing part and runs one way only: **anything that reads a stored `richDate`, or needs to know the club's timezone, belongs in `event-date.ts`** (`getRichDateDayKey`, `getTodayKey`, `groupEventsByDay` live there beside `getRichDateYearMonth`), and `calendar.ts` never imports either. That is what keeps the club's fallback timezone out of the calendar module: with a copy in each, bucketing an event into a day and judging it ended could drift onto different defaults, silently and with both test suites passing since each passes its own `TZ` in. (`event-date.ts` **is** the single definition site: `buildEventName.ts` and the crew page import `FALLBACK_TIMEZONE`/`resolveEventTimezone` from it rather than declaring their own `Asia/Taipei`.) Grids are built with `Date.UTC` integer arithmetic, never local `Date` mutators, and `buildMonthGrid` returns whole **weeks** so `DAYS_IN_WEEK` never escapes into a view. The last-step trap is `formatDayKey()`: plain `format(new Date('2026-09-05'))` prints the 4th anywhere west of Greenwich, so every date the calendar renders — weekday headings included — goes through that one function.
- `event-location.ts` — `resolveEventLocation()`: which venue an event shows and where its map link points. `pEvent` carries a `locationRef` to a `gLocation` plus a one-off `location`/`locationLink` pair the schema hides once a venue is referenced, and the reference wins. That one rule was written out identically in five components plus a sixth inline copy feeding the events JSON-LD — flipping the precedence meant six edits, and missing the JSON-LD one would have left structured data naming a different venue than the page it describes.
- `dateFnsLocale.ts` — the app-locale → date-fns locale map. A leaf module on purpose (NOT part of `i18n.ts`, which nearly everything imports — putting it there would drag both date-fns locale bundles into every consumer). Use it instead of hand-rolling `locale === 'zh_tw' ? zhTW : enUS`; its `satisfies Record<Locale, unknown>` breaks the build when a locale is added without a mapping. The calendar also reads `weekStartsOn` off it, which is what starts the English grid on Sunday and the Chinese one on Monday.
- `defineMetadata.ts` — also exports `omitPageMetadata()` / `WithoutPageMetadata<T>`: listing pages spread their whole query result into a client component, so they strip `sharing` and `availableLocales` (read only by `generateMetadata`) at that boundary rather than serializing them into the RSC payload for nothing. The return type drops the keys too, so a component that later reaches for `data.sharing` fails to compile instead of getting `undefined` at runtime.
- `size-measurements.ts` — `SIZE_UNITS` doubles as the order the cm/in control renders in, so reordering it changes the UI.
- `utils.ts` — `appendReferralParams()` / `REFERRAL_SOURCE` are what put UTM params on an outbound `purchaseLink`.

### Hooks (`src/hooks/`)

- `useScrollLock.ts` — Locks document scroll while an overlay is open, and keeps that lock honest across the page lifecycle (`pagehide` releases it, `pageshow` lets the owner close itself on a bfcache restore). Used by `CartDrawer` and `MobileMenu`; **the lock is global, so new overlays must go through this** rather than calling `scrollDisable`/`scrollEnable` directly. Those two open Base UI dialogs with `modal="trap-focus"` precisely so Base UI's own scroll lock stays off and this hook remains the only writer.
- `useScrollSpy.ts` — IntersectionObserver scroll-spy for in-page section navs + horizontal-strip auto-scroll; also exports `readRootPxVar()`.
- `useMediaQuery.ts` — A media query as reactive state, on `usePrefersReducedMotion`'s `useSyncExternalStore` model: it re-renders a consumer only when the query's ANSWER flips, where `useWindowDimensions` re-renders on every resize frame (42 calendar cells for one boolean) and needs a `mounted` flag to avoid a mismatch. `getServerSnapshot` is `false`, so a prerender always bakes the **query-false** branch — pick which branch that is deliberately, and keep it the one that is correct with no JS. **Write widths in `rem`**: Tailwind v4's breakpoints are rem-based, so `(min-width: 1024px)` and `lg:` disagree for anyone whose browser font size is not 16px, which is exactly when a JS-chosen branch and a CSS-hidden one can both be wrong at once. `useWindowDimensions.js` is **gone** — `ProductSubmission` was its last consumer and now uses `useMediaQuery('(max-width: 63.999rem)')`; phrased as max-width so the false-on-server branch is the Popover, which is the one that is correct with no JS.

### Commerce (Shopify + cart)

Products are **hybrid**: Sanity owns everything editorial (slug/routes, title, content, taxonomy, size charts, SEO, i18n) and Shopify owns commerce (price, compare-at, availability, variants, cart, checkout), coupled by `pProduct.shopify.handle`. The site is the store; the shopper only leaves at Shopify's hosted checkout.

**The rules that govern `src/lib/shopify/`, `src/app/api/shopify/`, `src/components/cart/` and the product detail page live in `.claude/rules/shopify-cart.md`**, which loads automatically on its `paths` frontmatter whenever those files are in play — several of its constraints (uncached carts, no `@inContext` on cart calls, the split `mainImage`/gallery ownership, the `cache()` argument-identity requirement) look like inconsistencies begging to be tidied up and must not be. Read it before touching any of those; if you are editing them and it has not loaded, open it explicitly.

### Environment Variables

The full list is in `.env.example`; the Shopify walkthrough is `docs/SHOPIFY-SETUP.md`. What those files don't say:

- **The Shopify vars are all optional.** Without `SHOPIFY_STORE_DOMAIN` plus a Storefront token, the whole integration no-ops and products render from the manual Sanity fields.
- `SHOPIFY_STOREFRONT_PRIVATE_TOKEN` (Headless channel) is preferred over `SHOPIFY_STOREFRONT_API_TOKEN` — the public one is throttled per buyer IP.
- `SANITY_READ_WRITE_TOKEN` is **only** for the one-shot `scripts/`, never read by the app. `SANITY_API_READ_TOKEN` cannot mutate.
- `SHOPIFY_ADMIN_API_TOKEN` is retired and read nowhere — a 38-char `shpss_` value is an app _client secret_, not an access token, and belongs in neither.

### Troubleshooting

- `Error: Failed to communicate with the Sanity API` → Run `sanity logout && sanity login`
- If `SANITY_API_READ_TOKEN` is missing at runtime, `src/sanity/lib/live.ts` will throw immediately on startup
